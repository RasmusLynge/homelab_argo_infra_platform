# Secrets via External Secrets Operator + Azure Key Vault

This GitOps repo needs to hold credentials (starting with the Cloudflare API token for cert-manager's DNS-01 solver, see [[0005-cert-manager-dns01-cloudflare]]) without committing them in plaintext. We chose External Secrets Operator (ESO) backed by Azure Key Vault over the simpler Sealed Secrets, since we already have an Azure subscription for other purposes — the marginal cost of one more Key Vault is near zero, and it keeps the actual secret values out of git entirely (not just encrypted in git, as Sealed Secrets/SOPS would do).

ESO authenticates to Key Vault via a **Service Principal** (`clientId`/`clientSecret`/`tenantId`), not Workload Identity or Managed Identity — Managed Identity only works for Azure-hosted compute, and Workload Identity requires Azure AD to reach this cluster's OIDC discovery endpoint publicly, which conflicts with the internal-only design. The Service Principal's client secret is itself a bootstrap credential: it is applied to the cluster manually (`kubectl apply`), never committed to git or synced by Argo CD — the one deliberate exception to "everything is GitOps" in this setup, since ESO can't use itself to fetch the credential it needs to reach ESO's backend.
